# Open WebUI comme interface et passerelle locale

## Position réelle

Open WebUI est une **plateforme auto-hébergée d’interface et de contrôle pour modèles**. Elle fournit une UI conversationnelle, la gestion des utilisateurs et des ressources, le routage vers Ollama et des API compatibles OpenAI, ainsi que des outils, connaissances/RAG, mémoire et automatisations. La documentation officielle la décrit comme fonctionnant entièrement hors ligne, mais elle peut aussi relayer des fournisseurs cloud : « offline » décrit la possibilité de déploiement, pas une garantie que toutes les connexions seront locales. Sources : [documentation d’accueil](https://docs.openwebui.com/) et [README du dépôt](https://github.com/open-webui/open-webui).

Pour un harness agentique, son rôle le plus exact est le **control plane** : identité, conversations, contexte, modèles, prompts, permissions, outils, connexions et progression du workflow. Elle n’est pas, à elle seule, un bac à sable d’exécution fiable. La documentation d’Open Terminal distingue explicitement Open WebUI (couche de contrôle) du runtime d’action (fichiers, shell, processus, paquets et artefacts) fourni par Open Terminal : [modèle d’intégration Open WebUI/Open Terminal](https://docs.openwebui.com/features/open-terminal).

Elle peut aussi servir de **passerelle locale** : son endpoint de chat est compatible avec l’API OpenAI et peut appeler des modèles Ollama, OpenAI et des modèles/fonctions Open WebUI ; des clés Bearer/JWT authentifient les appels. La documentation API qualifie toutefois l’ensemble de configuration « expérimentale » et susceptible d’évoluer : [API endpoints](https://docs.openwebui.com/reference/api-endpoints). Il faut donc traiter cette compatibilité comme une interface d’intégration à tester et versionner, non comme un contrat immuable.

## Mécanismes et étapes utiles

1. **Déployer et persister l’état.** Le dépôt officiel supporte Docker, pip/uv et Kubernetes. En Docker, `/app/backend/data` contient la base, la configuration et les extensions mises en cache ; le montage de ce volume est nécessaire pour éviter la perte de données : [README officiel](https://github.com/open-webui/open-webui).
2. **Connecter les modèles.** Open WebUI peut combiner Ollama local et des endpoints compatibles OpenAI, donc présenter une interface unifiée tout en gardant le choix du fournisseur. Les dépendances peuvent être locales (Ollama, moteurs d’embedding/extraction) ou distantes (API fournisseur, recherche Web, stockage objet), selon les fonctionnalités activées : [accueil](https://docs.openwebui.com/) et [README](https://github.com/open-webui/open-webui).
3. **Construire le contexte.** Les modèles peuvent être enveloppés dans des modèles personnalisés avec instructions, outils, connaissances et contrôle d’accès. Les documents peuvent alimenter une base de connaissances/RAG ; la mémoire, les notes et les canaux ajoutent du contexte persistant ou partagé. Ce contexte doit être classé par sensibilité et portée avant d’être injecté dans un agent : [README](https://github.com/open-webui/open-webui).
4. **Exposer des capacités.** Il existe plusieurs familles : fonctionnalités natives, Tools Python dans le processus, MCP HTTP, MCP via MCPO, serveurs OpenAPI et intégrations Open Terminal. Les trois dernières familles appellent un service externe par HTTP ; les Workspace Tools exécutent du Python dans l’environnement Open WebUI avec une surface beaucoup plus large : [taxonomie des Tools](https://docs.openwebui.com/features/extensibility/plugin/tools/).
5. **Orchestrer une boucle agentique.** Open Terminal ajoute un espace de travail avec shell, fichiers, exécution de code, processus, serveurs, previews et retour d’artefacts. La boucle attendue est comprendre, inspecter, agir, observer, réparer ou continuer, puis vérifier. En Docker, l’exécution peut être isolée ; en bare metal, l’agent agit directement sur l’hôte : [Open Terminal](https://docs.openwebui.com/features/open-terminal).
6. **Intégrer par API.** Le client du harness peut utiliser `POST /api/chat/completions`, `GET /api/models` et les API de gestion de modèles. Les endpoints acceptent des outils Open WebUI déjà configurés, y compris Tools Python, OpenAPI et MCP. Les clés API héritent des permissions de l’utilisateur qui les crée : [API endpoints](https://docs.openwebui.com/reference/api-endpoints) et [Authentication & Access](https://docs.openwebui.com/features/authentication-access/).
7. **Versionner la configuration.** Les modèles personnalisés sont exportables/importables en JSON. `/api/v1/models/import` est additif ; `/api/v1/models/sync` réconcilie et peut supprimer les modèles absents du payload. Ce mécanisme est utile pour une configuration déclarative en Git, mais `sync` doit être protégé par revue et approbation : [API endpoints](https://docs.openwebui.com/reference/api-endpoints).

## Artefacts et interfaces à exploiter

- **Interface utilisateur** : chats, modèles, knowledge bases, prompts, outils, mémoire, notes, canaux, fichiers, calendrier et automatisations ; utile pour l’opérateur et les validations humaines ([README](https://github.com/open-webui/open-webui)).
- **API REST/OpenAI-compatible** : façade programmable pour clients, bots, CI et un orchestrateur de harness ([API endpoints](https://docs.openwebui.com/reference/api-endpoints)).
- **MCP/OpenAPI/MCPO** : contrats de capacités externes. Préférer des serveurs séparés pour limiter le rayon d’explosion et rendre les appels observables ([Tools](https://docs.openwebui.com/features/extensibility/plugin/tools/)).
- **Workspace Tools/Functions** : plugins Python pour routage, filtres, actions et extensions ; ils ont accès au runtime serveur et ne sont pas une frontière de sécurité ([plugin system](https://docs.openwebui.com/features/extensibility/plugin/)).
- **Open Terminal et, pour le multi-utilisateur, Terminals** : runtime d’action séparé, espaces isolés par utilisateur, limites de ressources et cycle de vie lorsqu’on utilise l’orchestrateur Terminals ([Open Terminal](https://docs.openwebui.com/features/open-terminal)).
- **Données persistantes** : volume de données, base SQLite ou PostgreSQL, fichiers locaux ou stockage objet selon la configuration ([README](https://github.com/open-webui/open-webui)).
- **Observabilité et audit** : le projet annonce logs/audit et OpenTelemetry ; le durcissement recommande audit au niveau METADATA ou supérieur, format JSON, transfert SIEM et traces OpenTelemetry si disponibles ([hardening](https://docs.openwebui.com/getting-started/advanced-topics/hardening/)).

## Garde-fous à adopter

### Baseline obligatoire

- **Réseau privé par défaut.** Placer l’instance derrière VPN, proxy zero-trust ou reverse proxy avec limitation de débit, allowlist et protection brute-force. Ne pas l’exposer directement à Internet ; forcer HTTPS, cookies Secure/SameSite, en-têtes de sécurité et CORS strict. La documentation indique aussi de limiter `FORWARDED_ALLOW_IPS` au proxy de confiance : [Hardening](https://docs.openwebui.com/getting-started/advanced-topics/hardening/).
- **Identité forte.** Pour une organisation, préférer OIDC/OAuth ou LDAP, désactiver l’authentification locale si possible, mapper groupes/rôles IdP et automatiser le cycle de vie avec SCIM. Garder l’inscription fermée, exiger MFA et raccourcir la durée des tokens. Les permissions sont additives : les groupes ajoutent des droits et n’en retirent pas ; les ressources sont privées par défaut : [Authentication & Access](https://docs.openwebui.com/features/authentication-access/) et [Hardening](https://docs.openwebui.com/getting-started/advanced-topics/hardening/).
- **Clés et secrets séparés.** Conserver `WEBUI_SECRET_KEY`, clés fournisseur et credentials MCP dans un gestionnaire de secrets ou des variables protégées ; ne jamais les mettre dans un prompt, une image ou un dépôt. Les clés API Open WebUI héritent des privilèges du créateur : créer des comptes de service dédiés à portée minimale ([API](https://docs.openwebui.com/reference/api-endpoints)).
- **Extensions sous revue.** Tools, Functions, Pipes et Filters exécutent du Python arbitraire sur le serveur. Une personne pouvant importer/créer un Tool a en pratique un accès équivalent à l’exécution shell. Restreindre Workspace aux administrateurs de confiance, faire une revue de code, figer les versions et auditer régulièrement : [avertissement plugins](https://docs.openwebui.com/features/extensibility/plugin/) et [avertissement Tools](https://docs.openwebui.com/features/extensibility/plugin/tools/).
- **Désactiver l’exécution non requise.** Si le cas d’usage ne demande pas de code, désactiver `ENABLE_CODE_EXECUTION` et `ENABLE_CODE_INTERPRETER`. Désactiver aussi l’installation automatique de dépendances via `ENABLE_PIP_INSTALL_FRONTMATTER_REQUIREMENTS=false`. Si le code est nécessaire, isoler avec Open Terminal plutôt que l’ancien moteur Pyodide/Jupyter ; ne jamais exposer Jupyter sans protection : [Hardening](https://docs.openwebui.com/getting-started/advanced-topics/hardening/).
- **Isolation du runtime.** Utiliser Open Terminal en conteneur dédié, non-root, capacités Linux minimales, `no-new-privileges`, réseau segmenté, limites CPU/RAM/disque/processus, workspace par utilisateur et montage en lecture seule quand possible. Le bare metal est à réserver à un environnement explicitement approuvé : [Open Terminal](https://docs.openwebui.com/features/open-terminal) et [Hardening](https://docs.openwebui.com/getting-started/advanced-topics/hardening/).
- **Sorties réseau et SSRF.** Garder les protections SSRF, la vérification TLS et le blocage des IP privées/métadonnées ; ne pas activer le fetch local sans analyse dédiée. En air-gap, activer le mode offline et isoler aussi le réseau afin de fermer les canaux que l’application ne contrôle pas : [Hardening](https://docs.openwebui.com/getting-started/advanced-topics/hardening/).
- **Supply chain.** Utiliser les images officielles ou construire depuis le dépôt, pinner une release plutôt que `:main`/`:latest`, tester en staging et conserver un rollback. La maturité opérationnelle exige aussi sauvegardes restaurables, suivi des advisories et rotation des secrets : [Hardening](https://docs.openwebui.com/getting-started/advanced-topics/hardening/) et [Security du dépôt](https://github.com/open-webui/open-webui/security).

### Contrôles propres au harness

Le harness doit imposer une **allowlist de tools par modèle, groupe et tâche**, un budget de tours/tokens/temps, des limites de fichiers et de taille de sortie, un timeout par appel, une approbation humaine avant effets externes irréversibles, ainsi qu’un journal corrélant utilisateur, prompt, modèle, tool, arguments, résultat et artefact. Open WebUI fournit des permissions et des contrôles de catégories, mais le harness doit compléter les politiques métier et les validations ; une permission d’interface n’est pas une sandbox.

Pour chaque session, créer un workspace éphémère ou explicitement nommé, sans accès au volume global `/app/backend/data`, aux credentials ou aux sockets Docker. Filtrer les chemins, bloquer les symlinks sortants, limiter les domaines sortants et scanner les artefacts avant téléchargement ou remise à l’utilisateur. Les résultats de RAG, pages Web et fichiers doivent être traités comme **données non fiables** : ils ne doivent jamais modifier silencieusement la politique système.

## Limites et éléments à isoler ou éviter

- **Ne pas confondre interface et runtime sécurisé.** Open WebUI orchestre et présente ; son plugin in-process et certaines intégrations donnent une capacité d’exécution très large. La frontière d’action doit être Open Terminal conteneurisé ou un service tool externe isolé, pas un Tool Python importé à la volée ([Tools](https://docs.openwebui.com/features/extensibility/plugin/tools/)).
- **Ne pas importer le catalogue communautaire sans audit.** « Featured », populaire ou listé par la communauté ne signifie pas vérifié. La documentation dit explicitement que les plugins communautaires sont non audités ([plugin security warning](https://docs.openwebui.com/features/extensibility/plugin/)).
- **Éviter Pipelines pour une nouvelle conception.** La documentation les marque comme legacy et recommande Functions/Tools ou serveurs OpenAPI/MCP. Un déploiement historique peut rester isolé et migré, mais il ne doit pas devenir le nouveau bus de confiance ([Pipelines](https://docs.openwebui.com/features/extensibility/pipelines/)).
- **MCP/serveurs OpenAPI ne sont pas automatiquement sûrs.** Ils réduisent l’exécution in-process, mais déplacent la confiance vers un autre service, ses credentials, son réseau et son schéma d’arguments. Mettre chaque serveur en allowlist, avec identité de service et egress contrôlé.
- **Les fonctions “mémoire”, “automatisation”, recherche Web et cloud” augmentent la surface de données.** Les activer par défaut crée des voies de fuite ou d’actions différées ; les désactiver par modèle/groupe lorsqu’elles ne sont pas nécessaires. Les contrôles de catégories ne peuvent pas dépasser les flags globaux ni les permissions utilisateur ([Tools](https://docs.openwebui.com/features/extensibility/plugin/tools/)).
- **Ne pas surinterpréter l’étiquette “enterprise-ready”.** Le dépôt est actif et vaste, avec une politique d’advisories publiques, mais la page de sécurité liste aussi des vulnérabilités récentes, notamment autour de sessions, previews de documents et terminaux. Cela justifie le patch management, la revue des changelogs et la défense en profondeur ; cela ne permet pas de conclure à une sécurité parfaite ([Security advisories](https://github.com/open-webui/open-webui/security)).
- **Compatibilité et licence à vérifier.** L’API est documentée comme expérimentale. La licence Open WebUI impose notamment de conserver la marque dans les déploiements de plus de 50 utilisateurs sur une période glissante de 30 jours, sauf permission ou licence entreprise ; les composants sous licences antérieures conservent leurs termes ([API](https://docs.openwebui.com/reference/api-endpoints), [LICENSE](https://github.com/open-webui/open-webui/blob/main/LICENSE), [LICENSE_HISTORY](https://github.com/open-webui/open-webui/blob/main/LICENSE_HISTORY)).

## Maturité, dépendances et décision d’architecture

Le projet présente une surface fonctionnelle et opérationnelle importante : dépôt public actif, modes Docker/pip/Kubernetes, RBAC, SSO/LDAP/SCIM, API, plusieurs backends de stockage, observabilité et avis de sécurité publics ([README](https://github.com/open-webui/open-webui), [Security](https://github.com/open-webui/open-webui/security)). C’est une base crédible pour une **interface locale multi-utilisateur et un control plane**. La maturité ne doit cependant pas être confondue avec une garantie de sécurité de l’agent : les extensions peuvent exécuter du code arbitraire, l’API est signalée expérimentale, et le runtime terminal élargit fortement l’impact d’une erreur de modèle ou de permission.

Dépendances à expliciter dans le design : fournisseur de modèle (Ollama ou API OpenAI-compatible), base SQLite/PostgreSQL, stockage fichiers/local ou objet, Redis pour certains scénarios de sessions/scalabilité, proxy TLS/IdP, moteurs d’embedding/extraction et vector store pour RAG, plus Open Terminal/Terminals si l’agent doit agir sur fichiers et commandes. En mode cloud, les prompts, fichiers, résultats RAG et métadonnées peuvent sortir du périmètre local ; en mode local, les modèles et index peuvent rester sur site mais les outils Web, MCP et mises à jour réintroduisent des sorties réseau.

## Recommandation pour le harness NXUS

**À adopter :** Open WebUI comme façade opérateur et control plane local ; API OpenAI-compatible derrière un adaptateur versionné ; OIDC/LDAP + RBAC/groupes ; modèles et tools déclaratifs ; serveurs MCP/OpenAPI séparés et allowlistés ; Open Terminal conteneurisé pour les tâches qui exigent shell/fichiers ; audit centralisé, budgets et approbations dans le harness ; releases pinnées et sauvegardes testées.

**Optionnel :** mémoire, RAG, recherche Web, notes, canaux, automations, stockage objet, Redis, Terminals multi-utilisateur et plugins Functions/Tools après revue de menace et besoin démontré. Les activer par groupe/modèle, pas globalement.

**À éviter ou isoler :** Tools/Functions/Pipelines communautaires non audités, import Python par des utilisateurs ordinaires, Jupyter ou code interpreter non isolé, accès direct au volume de données ou à Docker, credentials partagés, `:main`/`:latest`, exposition Internet directe, fetch local/SSRF relâché, et Pipelines legacy pour tout nouveau composant.

La forme cible est donc : **Open WebUI (contrôle et UX) → adaptateur API/politique NXUS → modèles et serveurs tools autorisés → Open Terminal/Terminals isolé pour l’action**, avec approbation humaine sur les opérations à impact et audit indépendant de chaque frontière. Aucun élément des sources publiques consultées ne justifie de prétendre à un accès au code privé, aux prompts système privés ou à des fonctions non documentées ; ce rapport se limite aux interfaces et comportements attestés par les dépôts et documentations citées.
